Case File Search Bench

Four ways for an AI agent to search an investigation's evidence, measured on the same corpus and the same questions.

German Alvarez · November 2026

The question I couldn't answer

“Besides embedding and maybe full-text search, what search strategies are you familiar with? Let's say you have a corpus of 1 million documents and you need to find something.”

An interviewer asked me this recently, and I didn't have a good answer. This page is my answer, with measurements. I built the four strategies below, ran them against a real fraud-investigation corpus, and read how other agent harnesses solve the same problem.

The short answer. Pick the strategy by the shape of the question, not by the corpus. Exact identifiers want a normalized exact index. Questions about who, when and how many want structured queries, ideally written by the agent as a program. Fuzzy "find the email where" questions want hybrid ranking. In this benchmark, agents that could combine search, grep and metadata queries answered 92 to 100% of questions; retrieval alone answered 34%.

Four ways to search the same case file

Hybrid RAG

BM25 and embeddings fused with reciprocal rank fusion. The top 8 chunks go into one prompt. No tools.

Agentic grep

Claude Code's own Grep, Glob and Read over one text file per message. No index at all.

Typed tools

A corpus API as six tools: search, grep, messages, count, people, read.

Code mode

The same six functions as a JavaScript object in a QuickJS sandbox behind one execute tool. Only what the program prints comes back to the model.

Typed tools and code mode expose the same six functions, and both cap each call's output to the model at 8,000 characters. A program can process thousands of records inside the sandbox and print only the result. A tool call has to hand its rows to the model. That is the difference being measured.

Retrieval alone cannot count; code mode counts cheapest

  • Retrieval-only RAG cannot count. Top-8 hybrid RAG answered 2 of 15 aggregation questions and 0 of 10 hard ones on both models. It did reasonably on "find the email" (11 of 15 on both models) in one call with the fewest tokens. Use it as the first stage of a search system.
  • Identifiers need exact search and normalization. Every agent strategy found all 10 identifiers. RAG found 4. The questions write phone numbers with dashes and several messages use dots, which neither BM25 tokens nor embeddings bridge. Grep with a pattern like 703[-. ]227[-. ]8777 does.
  • Code mode and typed tools tie on accuracy and split on cost. Both use the same API and both answered 49 or 50 of 50. On the questions that need counting, code mode used far less context: on Sonnet's hard tier, 6,258 input tokens per question against 29,154 for typed tools. On Haiku's aggregation questions it made 1 call where typed tools made 10 (median), with 7,012 tokens against 38,827. The program does the counting, so raw rows never enter the model's context.
  • Code mode does not help when the model must read. On "find the email" questions, code mode used more tokens than typed tools (19,200 against 15,290 on Sonnet), even though its programs returned fewer characters (5,875 against 9,437). It took a second program more often (median 2 calls against 1), and every extra turn re-sends the whole context. This matches OpenAI's guidance to keep judgment and citation steps as direct calls and use code for bulk data stages.
  • Agentic grep is accurate but expensive. With no index, Claude Code's own tools reached 48 of 50 on Sonnet and 46 of 50 on Haiku, but it used 75,374 input tokens per question on Sonnet (8 times code mode) and 168,836 on Haiku (13 times). Every grep rescans 1.2 GB of files. That scan grows with the corpus, which is why Cursor built an index for regex search. At 20 to 30 million files I expect it to dominate (an estimate, not measured here).
  • The gaps hold on a smaller model. Haiku with code mode answered 50 of 50 for about a tenth of a cent per question. The weaker model widens the cost gap between strategies more than the accuracy gap.
  • Indexed strategies answer fastest. In a separate run of 8 questions on Sonnet, one question at a time, median latency was 5.4 seconds for RAG, 7.3 for code mode, 8.8 for typed tools and 29.4 for agentic grep. From src/timings.ts (median of 5 runs, runs/timings.txt): one ripgrep pass over the corpus takes 3.5 to 4.7 seconds, an indexed count takes 9 milliseconds, and a hybrid search takes 0.7 to 1.2 seconds. Agentic grep pays a full scan on every search, so its latency grows with the corpus. Treat all of these times as rough. The latency run had 8 questions with one trial each, and the timing run had a load average of about 26.

85 code-mode implementations, compared

A model decides what code to write; the sandbox decides what that code can do. So each sandbox can be tested on its own, with fixed code and no model in the loop. 69 implementations ran on this machine against the same twelve probes, with their defaults and, where a project exposes stricter settings, with the strictest ones. 10 could not run here (hosted services that need an account, stubs, setup crashes) and 5 come only from documentation. A second review agent, separate from the one that ran the probes, then reran the gate probes for 13 candidates and tested what a shared server needs: whether one user's runaway program delays another's. Every cell has evidence in the repo under research/probes/; hover a cell for the detail.

  • For TypeScript, Vercel AI SDK Code Mode (or Vercel Run, the engine under it). QuickJS in WebAssembly in a worker thread. With defaults it held every limit, ran tool calls in parallel, kept other users' requests within about 0.3 s while a neighbor misbehaved, and replaced host errors with a generic message. Programs must return their result, because console.log output goes to the server's stdout. Make tools honor the abort signal, because calls already sent keep running when a program fails.
  • For Python, Pydantic AI Harness CodeMode, or FastMCP CodeMode for MCP servers. Both run Pydantic's Monty interpreter in a worker process with time and memory limits on by default and parallel tool calls. Mask host error text yourself (mask_error_details=True in FastMCP). Strands is close behind if you set its timeout, but it cannot mask host errors. In this repo, Monty used directly did better than either wrapper (see the engines section).
  • OpenCode and Claude Code's new Code Modes are safe at the language level but have no memory limit. OpenCode also allows fetch by default and its execute tool has no time limit; a memory bomb took its host process to 4.3 GB in a second.
  • Most implementations isolate code. Far fewer enforce limits. 30 of 69 let model code reach the host, mostly by running it with exec, IPython or a host-seeded node:vm. 33 had no working time limit and 40 no working memory limit with defaults. The causes were timers inside the guest that a loop never yields to, memory options accepted and ignored, and whole-process crashes that end every session.
  • A shared server needs tests the usual probes skip. A second review agent found one user's loop freezing everyone (engines on the host's main thread), guest logs growing host memory past 4 GB (UTCP, TanStack Node), recursion outside the memory budget killing a gateway (Bifrost), and database URLs in tool errors reaching the model in most implementations.
  • Tool discovery is keyword search or a searchable catalog, not embeddings. Pi and FastMCP use BM25; OpenClaw, Claude Code and Qwen Code let the program search a catalog; the Vercel AI SDK and langchain-quickjs can optionally defer tools to the provider's tool search, though by default they put every signature in the prompt. Cursor's current docs say its agent search is Instant Grep, a local regex index.
  • The probes found five bugs in this repo's own sandbox, all fixed and re-tested. Shared asyncify state, an import that wedged later runs, a 512 MB memory cap that never applied (3.08 GB before the fix), one runaway program freezing every request for 60 s, and a bridge call that could make the host serialize the whole corpus. It now runs each program in its own worker thread with a host-side wall clock.
  • Retention matters for case data. Anthropic's programmatic tool calling docs list zero data retention and HIPAA as not eligible, with data retained up to 30 days; OpenAI's docs say its version supports zero data retention.

Each was probed with the same suite, timed while a neighbor program misbehaved, and run on 12 benchmark questions with exact answers on Claude Sonnet.

What I would build for 20 to 30 million case files

  • Ingest once into typed records. Every file gets a stable id, a content hash and page or row spans. Phone numbers, case numbers, plates and accounts get normalized into their own columns, so 773.555.0142 and (773) 555-0142 are one value. Copies collapse by hash, as the 517,401 to 255,154 dedupe here did.
  • Index three ways. An exact identifier index, a full-text index, and a vector index with per-case filtering. Grep without an index gets slower as the corpus grows: here one pass over 1.2 GB took 3.5 to 4.7 seconds and agentic grep was the slowest strategy. At 20 million files I expect each pass to take minutes (an estimate, not measured).
  • Give the agent a typed API and let it write code against it in a sandbox. The program does the filtering, counting and joining. Only the result and its citations come back to the model. From the sandbox tests: run one isolate, worker or process per execution, enforce time and memory from outside the guest and test that they hold, keep credentials and case-access checks on the host side of the bridge, cap concurrency per user, sanitize host errors, and use an async bridge so one program can query several indexes at once. Off the shelf, that is Vercel Run (or AI SDK Code Mode on top of it) in TypeScript, and Pydantic's Monty interpreter in Python, used directly or through Pydantic AI Harness if you are on Pydantic AI.
  • Check citations outside the model. Re-read every cited span and recompute every number from the cited rows before an investigator sees it. My take-home for a role like this did exactly that for evidence spreadsheets.
  • Grade it with exact ground truth. Counts and identifiers have one right answer, so most of an eval set can be graded by code, not by an LLM judge.

Method and limits

  • Corpus: the public Enron corpus from CMU. 517,401 files deduplicated to 255,154 messages by sender, date, subject and body, then split into 412,117 chunks of up to 1,200 characters, embedded locally with bge-small-en-v1.5.
  • Questions: 15 aggregation and 10 identifier questions with truth from SQL, 15 paraphrased "find the email" questions written by an LLM from seed emails, and 10 hard questions with truth from ripgrep joined to metadata.
  • "Find the email" is scored against the seed email plus every message any strategy cited that an LLM judge says states the answering fact. Seed replies often quote the original, and the original is an equally right citation. Every strategy is scored against the same pool.
  • One trial per question and strategy. The intervals in the tables are Wilson intervals over these 50 questions; they do not capture run-to-run variance, so small accuracy gaps are not meaningful. Token counts and tool calls are exact.
  • Scoring. Counts, dates and addresses must match exactly. Identifier questions need both the right message cited and the right sender. "Find the email" questions need a relevant citation and an answer an LLM judge accepts. Citations are not checked on count and date questions. Two judges on different models agreed on 29 of 30 relevance calls.
  • The hard tier was added after the first 40 questions saturated. It was designed to need counting over text matches, so treat it as an exploratory follow-up, not a held-out test.
  • RAG here is one configuration: top 8 chunks, at most 4 chunks per message, one call. A RAG pipeline with a SQL step would answer counting questions; this measures retrieval-only RAG.
  • After the runs, the sandbox probes and reviewers found five bugs in this repo's code-mode sandbox (see the comparison above). All are fixed and live questions still answer correctly, but the published code-mode runs used the original sandbox.
  • After the runs, a review found that filtered keyword search filtered after taking the global top results, which could only have hurt typed tools and code mode. It is fixed in the code; the published runs used the old version.
  • Latency comes from a separate run of 8 questions on Sonnet, one question at a time.
  • The published runs used Bun, the original sandbox and a grep that blocked the server while it ran. The repo now runs on Node 24 with pnpm, defaults to the Vercel Run engine and greps asynchronously. The 12-question engine reruns above used the new setup.
  • Models run through the Claude Agent SDK with user settings, plugins and MCP configuration isolated. Costs are list-price estimates the SDK reports.
