Case File Search Bench

Four ways for an AI agent to search an investigation's evidence, measured on the same corpus and the same questions.

German Alvarez · November 2026

The question I couldn't answer

“Besides embedding and maybe full-text search, what search strategies are you familiar with? Let's say you have a corpus of 1 million documents and you need to find something.”

An interviewer asked me this recently, and I didn't have a good answer. This page answers it with measurements from four strategies run on a real fraud-investigation corpus.

The short answer. Pick the strategy by the shape of the question. Exact identifiers want an exact index, counting questions want a program the agent writes, and fuzzy "find the email" questions want hybrid ranking. Agents that combined search, grep and metadata answered 92 to 100% of questions; retrieval alone answered 34%.

Four ways to search the same case file

Hybrid RAG

BM25 and embeddings fused with reciprocal rank fusion. The top 8 chunks go into one prompt. No tools.

Agentic grep

Claude Code's own Grep, Glob and Read over one text file per message. No index at all.

Typed tools

A corpus API as six tools: search, grep, messages, count, people, read.

Code mode

The same six functions in a sandbox behind one execute tool. Only what the program prints comes back to the model.

Typed tools and code mode expose the same functions, with output capped at 8,000 characters. A program can process thousands of records in the sandbox and print only the result. A tool call has to hand its rows to the model.

Same questions on Haiku 5.5

A smaller model, to check whether the gaps hold.

Retrieval alone cannot count; code mode counts cheapest

  • Retrieval-only RAG cannot count. Top-8 hybrid RAG answered 2 of 15 aggregation questions and 0 of 10 hard ones on both models. It answered 11 of 15 "find the email" questions in one call with the fewest tokens, so it works as a first stage.
  • Identifiers need exact search. Every agent strategy found all 10 identifiers and RAG found 4. The questions write phone numbers with dashes and several messages use dots, which neither BM25 nor embeddings bridge. Grep with 703[-. ]227[-. ]8777 does.
  • Code mode and typed tools tie on accuracy and split on cost. Both answered 49 or 50 of 50. On Sonnet's hard tier, code mode used 6,258 input tokens per question against 29,154 for typed tools, because the program does the counting and raw rows never enter the model's context. On "find the email" questions the order flips (19,200 against 15,290), because reading needs the model.
  • Agentic grep is accurate but expensive. It reached 48 of 50 on Sonnet with 75,374 input tokens per question, 8 times code mode. It was also the slowest, at a median 29.4 seconds against 7.3 for code mode and 5.4 for RAG (8 questions, one trial each, so rough). Every search rescans 1.2 GB, and that cost grows with the corpus.
  • The gaps hold on a smaller model. Haiku with code mode answered 50 of 50 for about a tenth of a cent per question.

85 code-mode implementations, compared

A model decides what code to write; the sandbox decides what that code can do. So I tested each sandbox with fixed code and no model. 69 implementations ran here against twelve probes, with defaults and with the strictest settings each exposes. 10 could not run here and 5 come only from documentation. The evidence for every cell is in the repo under research/probes/.

  • For TypeScript, Vercel AI SDK Code Mode (Vercel Run underneath). QuickJS in WebAssembly in a worker thread. With defaults it held every limit, ran tool calls in parallel and kept host error text away from the model.
  • For Python, Pydantic AI Harness CodeMode, or FastMCP CodeMode for MCP servers. Both run Pydantic's Monty interpreter with time and memory limits on by default. In this repo, Monty used directly did better than either wrapper.
  • Most implementations isolate code. Far fewer enforce limits. 30 of 69 let model code reach the host, 33 had no working time limit and 40 no working memory limit with defaults. OpenCode and Claude Code's Code Modes have no memory limit; a memory bomb took OpenCode's host process to 4.3 GB in a second.
  • The probes found five bugs in this repo's own sandbox, all fixed and re-tested. The worst was a 512 MB memory cap that never applied (3.08 GB before the fix).

  • All seven answered 12 of 12 questions on Sonnet and passed every safety probe. The engine changes how a program runs, not whether the model finds the answer.
  • The default is Vercel Run. It takes 3.7 ms per execution, runs 5 corpus calls in 220 ms instead of 1,008 ms, and needs no native add-on. isolated-vm is faster (1 ms) for CPU-heavy programs but runs only on Node. For Python, py-monty kept pace at 4.7 ms.

What I would build for 20 to 30 million case files

  • Ingest once into typed records. Stable ids, content hashes, and identifiers normalized into their own columns, so 773.555.0142 and (773) 555-0142 are one value.
  • Index three ways. Exact identifiers, full text, and vectors filtered per case. One unindexed grep pass over 1.2 GB took 3.5 to 4.7 seconds here; at 20 million files I expect minutes (an estimate, not measured).
  • Let the agent write code against a typed API in a sandbox. The program filters, counts and joins, and only the result and its citations reach the model. Enforce time and memory from outside the guest, and keep case-access checks on the host.
  • Check citations outside the model. Re-read every cited span and recompute every number before an investigator sees it. Counts and identifiers have one right answer, so code can grade most of the eval set.

Method and limits

  • The corpus is the public Enron corpus from CMU. 517,401 files were deduplicated to 255,154 messages, split into 412,117 chunks and embedded locally with bge-small-en-v1.5.
  • There are 15 aggregation and 10 identifier questions with truth from SQL, 15 "find the email" questions, and 10 hard questions with truth from ripgrep joined to metadata. The hard tier was added after the first 40 saturated, so treat it as exploratory.
  • Counts, dates and identifiers must match exactly. "Find the email" answers need a relevant citation and an LLM judge's approval; two judges on different models agreed on 29 of 30 relevance calls.
  • One trial per question and strategy, so small accuracy gaps are not meaningful. Token counts and tool calls are exact. Latency comes from a separate run of 8 questions on Sonnet, one at a time.
  • RAG here is retrieval only: top 8 chunks, one call. A RAG pipeline with a SQL step would answer counting questions.
  • The published runs used Bun and the original sandbox, before the sandbox fixes, the Node 24 port, asynchronous grep and a fix to filtered keyword search that could only have hurt typed tools and code mode. The engine reruns used the new setup.
